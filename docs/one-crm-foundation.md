# ONE CRM — foundation (draft)
This module is deliberately not mounted in the live server and has no message sender or persistent customer store. It operates on synthetic or authorized pseudonymous ticket evidence only.

## Source adapter contract
Use existing server-side store authorization and tenant membership. Do not use browser-side credentials or expose customer tokens from aggregate analytics endpoints. Read complete verified ticket windows from the sales adapter; do not silently accept truncated or unavailable data. Normalize a stable tenant-scoped ticket identity (including date/register where needed), store, business date, customer token, and integer signed net monetary amount in one verified currency. Exclude voided receipts; reconcile returns and duplicate receipts against the ERP. Anonymous transactions remain anonymous. The window is an observation window, not lifetime history. A separate enrollment/identity source is needed for customers without purchases.

## Storage design (proposed, not migrated)
Separate CRM service and database with tenant-scoped foreign keys, row policies, encryption and audited role grants. Entities: tenant, brand, store, customer, source_identity, contact_point, consent_event, suppression, purchase, purchase_line, loyalty_event, segment, segment_version, journey, journey_version, campaign, message, delivery_event, holdout_assignment, attribution_event, sync_run, audit_event. Identity resolution uses verified source keys; no automatic cross-brand merging. Consent and contact data stay separate from analytics tokens. Explicitly approved contact scope is required for activation.

## Release gates
1. Confirm ownership, private storage and permitted processing, auth, source coverage, stable token join and reconciliation.
2. Read-only authorized customer profiles and dynamic segments; handle unknown data honestly, pagination and access tests.
3. Provider sandbox, webhook signature validation, idempotency, outbox/queue, retries, suppression and opt-out, templates, channel permissions, frequency limits, approval workflow and kill switch. No real sends until approved.
4. Campaign experiments with randomized holdout and net margin after campaign costs, not observational sales alone.
5. B2B extension through organizations, contacts, pipeline, activity, tasks and opportunities, separate permissions and legal scope.

## P3.2 — signed export pilot R0.29
The existing Dynamics sales basket extraction is positive-sales-oriented: `includedRetailSaleRow` excludes nonpositive sales and the existing TTC calculation takes absolute tax. Do not reuse it as a signed CRM source or change its KPI semantics. Build a separately authorized export with verified status/sign/discount/tax conventions and actual store-day closure. The pure `reconcileSignedExport` adapter accepts exact signed decimal TTC strings, normalized opaque IDs, company/register/transaction/line identity, and a complete manifest; excludes voided lines, blocks conflicting duplicates and inconsistent identity, and reconciles both signed line totals and ticket totals against independently sourced references. A mixed receipt can contain negative lines but still be a positive ticket. The reference must include both sets of controls; a shared lineage or unverified mapping blocks the import. Metadata flags alone are not proof. No live Dynamics calls, real data, imports or writes are enabled. Before production: private approved runtime, verified field mapping on real closed days with finance, server-derived authorization, validated independent extracts, then private read-only API. No public data upload.

## P3.3 — access control foundation R0.30
The new internal authorization gateway requires a verified active principal (issuer + subject) supplied by trusted server authentication, fresh tenant membership and explicit registered store grants. Browser request fields cannot supply roles, principals or allowed stores. It checks scope before accessing evidence, supports analyst/marketer/reviewer/data_admin/brand_admin roles, never grants send permission, and returns only allowlisted aggregate fields. Cohorts below 10 are suppressed; repeated differencing and query-budget abuse remain open. The membership schema is a draft with forced RLS/default deny and tenant-bound foreign keys, not deployed. No live IdP verification, server repository, route, service policy, or login has been wired. Brand admin can prepare and review in this draft matrix; production approval must enforce distinct actors and audit state transitions. Do not treat the browser simulator as security. Before enabling a private read-only endpoint, implement actual signed session validation, trusted grant queries, revalidation/revocation and anti-inference controls; ensure non-owner/non-BYPASSRLS execution and run penetration tests.

## P3.4 — generative Copilot contract R0.31
Server-only transport for Vercel AI Gateway Chat Completions, with an explicitly approved configured model and credential, timeout, no retries or automatic fallback. No provider called in CI or sandbox. The LLM receives only an approved synthetic question and permitted store list, returns exactly four JSON fields, and has no tools or raw data access. Strict validation reconstructs allowlisted segment expressions, rejects unknown fields and unauthorized stores. Trusted session/scope and query-budget reservation must run before a provider request; the existing audience gateway must reauthorize the read and suppress small cohorts. Answers are deterministic allowlisted aggregates; campaign output is a proposal only, not a persisted draft or permission to send. This does not prove the model correctly understands natural language, nor fully prevent prompt injection or privacy attacks. Before a live synthetic test: configure a private runtime, verify model availability/compatibility and provider data retention, approve spend/limits and credentials, implement real trusted auth, query budget and audit, and evaluate intent accuracy and adversarial prompts. Real-data mode remains disabled; no actual user or client information may be transmitted. No external call or billable request performed.

## P3.5 — delivery contract R0.32
Synthetic-only state machine (demo-prefixed IDs), separate author/reviewer, approved revision, template, consent/history completeness, per-recipient contactability/frequency and budget gate. Stable queue key per tenant/campaign/customer; recheck consent/frequency/contactability and emergency stop before mock submission. An ambiguous result is not retried, terminal conflicting receipts are rejected, receipt replay is idempotent within one job, opt-out is recorded locally. This is not an outbox or actual transport. Production requires durable transactionally unique reservations, atomic budget/frequency enforcement across campaigns, separate authenticated approver, versioned approved content, verified provider template, quiet hours, signed webhook verification and provider-account binding, tenant-wide deduplication and opt-out ledger, recovery/reconciliation of unknown delivery, cost controls and provider sandbox credentials. No real send or spend. Copilot UI overlap fixed by replacing nested aside inheriting fixed navigation styles.
