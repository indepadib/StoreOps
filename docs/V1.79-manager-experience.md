# StoreOps V1.79 — Manager Experience Contract

## Product rule
StoreOps is not a mini-Dynamics. It is a decision assistant for the store manager.

The manager must never need to understand D365 entities, warehouses, inventory dimensions, price groups or technical statuses to decide what to do.

Every main flow follows:

**Intent → Context → Recommendation → One primary action → Confirmation → Next action**

## Manager navigation
For a store manager, the primary mobile navigation is limited to four destinations:

1. **Aujourd'hui** — the 3–5 actions that matter now.
2. **Scanner** — scan/search an item, understand the situation, act.
3. **Équipe** — employees, shifts, attendance, objectives.
4. **Plus** — full operational modules, history, settings allowed to the role.

There is no store selector for a store manager. Their assigned store is implicit everywhere.

The Ops Director keeps the network/store selector and network control tower.

## Store and supply visibility
A manager can see only their own store as an operational perimeter.

For inventory/replenishment decisions, they may additionally see the **supply warehouse that feeds their store**. This does not grant network or warehouse-operational rights; it is supply context only.

Primary item stock card:
- Store available stock
- Store physical stock when useful
- Supply warehouse available stock
- Incoming / already ordered quantity
- Estimated cover in days
- Recommended action

Technical dimensions live behind “Détails stock & lots”.

## Batch semantics
The primary stock number is the aggregation of **all eligible inventory rows/batches** for the selected store warehouse.

Never display a random single batch as total stock.

Exclude or separate non-sellable states when the D365 mapping exposes them (blocked, quarantine, expired, etc.).

Batch detail is progressive disclosure:
- batch/lot id
- sellable/available quantity
- physical quantity
- location when available
- expiry/DLC/DDM when available
- FEFO priority

For replenishment, StoreOps reasons on aggregated sellable stock. Batch choice for warehouse picking remains a warehouse/WMS concern.

## Replenishment decision engine
The manager should not calculate a transfer quantity manually unless they choose to override the recommendation.

Inputs, when available:
- store available stock
- supply warehouse available stock
- open transfer/inbound quantity
- open supplier purchase quantity
- daily sales history
- weighted recent velocity (7d/28d)
- day-of-week effect
- current/future retail promotion uplift
- lead time
- safety-stock / cover policy
- case pack / purchase unit
- minimum order quantity
- shelf capacity when configured
- stock anomalies and negative quantities

Core decision:

`target demand = forecast daily demand × (lead time + safety cover)`

`net need = target demand - store available - confirmed inbound`

`recommended qty = round up positive net need to the case pack`

Then cap/classify against supply warehouse availability.

Decision states:
- **OK** — enough stock, no action.
- **REPLENISH** — warehouse can cover the recommendation.
- **PARTIAL** — warehouse can only partially cover.
- **WAREHOUSE_OUT** — store needs stock but supply warehouse has none.
- **CHECK_STOCK** — negative/inconsistent stock; inventory check first.

The manager sees the decision in plain French, not the formula.

Example:

> Ciel Pet 5L
> Val Fleuri: 3 disponibles · ~1 jour
> Entrepôt: 31 disponibles
> Recommandation: commander 12
> [Commander 12]
> Modifier · Détails stock & lots

## Workforce model
An **employee is not automatically a StoreOps user**.

### Employee lifecycle
A store manager can manage employees in their own store, subject to governance settings:
- create employee
- employee code / matricule
- first/last name
- operational role
- contract type
- contract start
- optional contract end
- active / notice / ended
- contact fields when permitted

Ending a contract never deletes history.

### StoreOps account
Application access is a separate object linked to an employee when required.

Account creation and privileged-role assignment remain governed by permissions. A manager cannot make themselves Ops Director or expand their store perimeter.

### Shifts
The manager can:
- create a shift
- assign an employee
- choose date/start/end
- set operational role for the shift
- duplicate a day/week
- detect overlaps
- see coverage gaps before publishing
- cancel/reassign a shift while keeping audit history

The opening attendance screen is generated from the published shifts for that day.

### Objectives
Objectives can be assigned by employee, role, store or period.

Examples:
- price/promo controls completed
- shelf replenishment tasks
- loss reduction target
- customer/NPS objective
- availability target
- training/quality objective

Every objective has a target, period and simple progress state. Objectives must never turn the opening flow into an HR dashboard; they live in Team/employee detail and surface on Today only when action is needed.

## “Aujourd'hui” experience
The home page is not a dashboard wall.

Show at most 3–5 prioritized actions.

Examples:
- “Réception prévue à 10:30 — 12 lignes à contrôler”
- “6 articles à réapprovisionner — 4 disponibles à l’entrepôt”
- “1 DLC critique aujourd’hui”
- “Équipe incomplète à 07:45 — 1 poste caisse non couvert”

Each card has one clear CTA: **Commencer**, **Traiter**, **Scanner**, **Affecter**.

Secondary KPIs and health score are available lower in the page, never before the actionable list.

## Scan experience
Scan/search must be the fastest path in the app.

1. scan barcode or type EAN/SKU/name
2. immediate item card
3. simple status and recommendation
4. one primary action based on context
5. optional details

Possible primary actions:
- Commander / créer transfert
- Contrôler stock
- Corriger prix/promo
- Ajouter DLC
- Déclarer perte
- Ouvrir incident

## UX quality bar
- mobile first
- large tap targets
- one dominant CTA per step
- no technical jargon on primary screens
- progressive disclosure
- defaults and recommendations before manual fields
- undo/cancel where safe
- confirmation screens that explain what happened
- never lose work when navigating back
- readable with one hand in store conditions
- skeleton/loading states rather than blank screens
- graceful degraded mode if one D365 domain is unavailable

## Permission contract
### Store Manager
- own store only
- can see supply warehouse stock only as replenishment context
- manage own-store employee records/shifts/objectives within policy
- execute store operational actions

### Ops Director
- network view
- switch stores
- define network policies
- view and manage all stores
- manage privileged access subject to admin governance

### Quality/Audit
- read network quality/audit information
- quality controls according to granted profile
- no unrestricted operational posting

### Admin
- account and permission governance
- store/supply mappings
- integration configuration

## Delivery sequence
1. Manager navigation + Today/Scan information architecture.
2. Store + supply warehouse stock context, all-batch aggregation and details contract.
3. Replenishment recommendation engine with explainable inputs and overrides.
4. Employee lifecycle + shift planning + opening attendance generated from shifts.
5. Objectives.
6. Configuration/admin UX for stores, users, permissions, mappings and policies.
7. Polish: transitions, loading/error states, microcopy, accessibility and mobile ergonomics.

This document is a product contract: new features should be rejected or redesigned if they make the manager’s primary journey harder to understand.
